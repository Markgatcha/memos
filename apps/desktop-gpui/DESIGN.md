# MemOS Desktop Architecture & Read-Only Design (`DESIGN.md`)

## 1. Strict Read-Only SQLite Boundary & Opt-In MCP Writer

MemOS Desktop opens the SQLite store **strictly read-only** from Rust (`src/core/db.rs`):

1. **Driver flags**: Every connection opens with `OpenFlags::SQLITE_OPEN_READ_ONLY` (`src/core/db.rs`).
2. **Engine guard**: Immediately after opening, the connection executes `PRAGMA query_only = ON;` and `PRAGMA busy_timeout = 5000;` so concurrent WAL writers (`memos` CLI or MCP server) never cause spurious `SQLITE_BUSY` failures while the desktop client reads consistent snapshots.
3. **Two deliberate write paths, both explicit**: Every existing store is opened read-only for browsing. The only DDL in the crate lives in (a) `core/store_init.rs`, reachable solely from **Create memory store** against a path that does not yet hold a store, and (b) `core/store_optimize.rs`, reachable solely from **Optimize store** in Settings, which only adds missing `CREATE INDEX IF NOT EXISTS` entries (recency, provenance and other read-path indexes) and never touches rows or tables. Both refuse symlinks and non-store files, and store creation re-checks the opened file before writing. There is still no `INSERT`, `UPDATE`, `DELETE`, or `DROP` path in Rust. Harness detection (`src/core/harness/`) also inspects config files read-only (`applied = false` on `InstallPlan`).

When users opt into **Write mode (MCP)** in Settings (disabled by default), writes never touch SQLite directly from Rust. First, `SchemaInfo::check_writer_preflight` (`src/core/db.rs`) verifies the store contains required write columns/tables (`nodes.metadata`, `nodes.valid_from/valid_to`, `edges.metadata`, `edges.valid_from/valid_to`, `node_tags`, `contradictions`). Older stores keep write mode disabled and show a human migration banner without exposing raw SQLite errors. On compatible stores, `WriteBridge` (`src/core/write_bridge.rs`) lazily spawns one persistent MCP child process (auto-discovering `memos` on `PATH`, then a sibling/repo `dist/cli.js mcp`, falling back to `npx -y @mem-os/sdk mcp`; users can switch via **Use local CLI** in Settings) with `MEMOS_DB_PATH` and `MEMOS_MCP_TOOLS=all`, discovers capabilities via `server/discover` and sends the per-request `2026-07-28` `_meta` envelope (`io.modelcontextprotocol/protocolVersion`, `clientInfo`, `clientCapabilities` — no handshake; falling back to legacy `initialize` `2025-11-25` only on `-32022`/`-32601`/invalid-envelope responses), gates specialized tools (`memos_review`, `memos_ingest`, `memos_audit_answer`, `memos_explain_recall`) against the returned tool list so older `24`-tool writers surface an actionable capability card instead of raw `-32602` RPC errors, enforces a `10 s` call timeout (`60 s` for `memos_ingest`) and `CREATE_NO_WINDOW` on Windows, and cleans up the subprocess on `Drop` or mode disable:

- **Create**: `memos_store` (content, type, pool, tags, namespace, context).
- **Edit**: `memos_store` followed by `memos_supersede` against the previous memory ID so history and provenance stay intact.
- **Forget**: confirmation modal + `memos_forget`.
- **Review queue**: lists pending candidates directly from SQLite in read-only mode (`ReadOnlyStore::load_pending_review`, no writer process), switches to `memos_review` (`action: "list"`) when write mode is active, and gates **Approve** / **Reject** mutations on write mode (`action: "approve"` / `"reject"`). The review nav badge is fed by the same query so it agrees with the queue.
- **Ingest files or folder**: modal UI over `memos_ingest` (`60 s` timeout, native folder picker via GPUI `prompt_for_paths`, presets, extensions, chunk size, recursive flag) with zero Rust document parsing.
- Errors map SQLite/MCP codes into short, actionable messages inside a non-blocking header banner showing the failing command, **Retry**, and **Settings** so reading and browsing remain uninterrupted.

## 2. Why MemOS Desktop Queries SQLite Directly (And Bridges Writes Only When Enabled)

Rather than embedding an Electron shell, WebView, or unconditionally spawning Node for reads:

- **Cold start under 400 ms**: Native binary startup avoids V8 isolate initialization, TypeScript module resolution, and IPC handshakes.
- **Predictable memory footprint (< 200 MB at 50k nodes)**: Direct `rusqlite` queries project only light list-row fields (`substr(coalesce(summary, content), 1, 220)` in SQL) and intern repeated namespaces, types, sources, harnesses, provenance tiers, and tags into `gpui::SharedString` handles. The list fetches an initial `LIST_PAGE_SIZE` (500) page and appends `LIST_NEXT_PAGE_SIZE` (250) pages cleanly via SQL keyset pagination on `(sort_value, id)` as the user scrolls or navigates near the bottom; graph snapshots scan up to 50k matching rows so cluster counts stay accurate. Full `content`, `metadata`, linked `edges`, and `contradictions` are fetched lazily only for the actively selected node.
- **Self-contained distribution**: `rusqlite` uses the `bundled` feature (`libsqlite3-sys`), eliminating runtime Node or system SQLite version mismatches while matching MemOS's exact FTS5 (`porter unicode61`) tokenizer behavior directly in SQL.
- **Zero UI-thread stalls**: Every SQLite query, FTS5 search (120 ms debounced), schema introspection, spatial-grid graph layout (up to 2,000 visible nodes + cluster nodes via `lyon` curves), and harness inspection runs on GPUI's background executor (`cx.background_executor().spawn(...)`) with generation counters cancelling stale in-flight requests.
- **One warm connection**: `core/store_cache.rs` keeps a single read-only connection alive for the resolved store and reopens it only when the main-file/WAL stamp changes, so searches, pages, details, and graph loads reuse the statement cache and 16 MB page cache instead of re-introspecting the schema per query.

## 3. Forward/Backward Schema Introspection

Because user databases may come from older or newer MemOS CLI releases, `ReadOnlyStore::open` never hardcodes optional columns or auxiliary tables:

- `SchemaInfo::introspect` queries `sqlite_master` and `PRAGMA table_info(...)` for every table/view.
- Missing auxiliary tables (`edges`, `node_tags`, `embeddings`, `contradictions`, `procedural_lessons`, `recall_traces`, `tamper_log`, `entity_index`, `nodes_fts`) degrade cleanly to empty facets/edges and SQL `LIKE` fallback when `nodes_fts` is absent.
- Optional `nodes` columns (`summary`, `importance`, `confidence`, `evidence_count`, `provenance`, `trust_score`, `quarantined`, `valid_from`, `valid_to`, `expires_at`, `metadata`, etc.) are dynamically projected with safe SQL defaults whenever absent.

## 4. Sensitive Data Isolation

Memory text and search queries are treated as sensitive user data:

- `tracing` logs emit only structured counts, durations, table names, schema column counts, and IDs.
- Database and UI errors are sanitized before rendering or logging.
- Both Sentry's `before_send` hook and local crash report writers (`src/telemetry.rs`) pass all strings, frames, breadcrumbs, tags, and `extra` payloads through `scrub_sentry_event` / `scrub_text` to redact active queries, inspected memory samples, filesystem paths, OS usernames, and hostnames.

## 5. Startup Timeline & Performance Design

- **Phase instrumentation (`src/telemetry.rs`, `--startup-report <path>`)**: records monotonic spans for `process_start`, `settings`, `telemetry_init`, `gpui_app_init`, `window_open` (with `app_view_new`, the app's own `MemOSApp::new` inside it), `first_render`, `first_frame`, `db_open`, `overview`, and `first_list_page`, emitting one non-sensitive `tracing` line per phase plus optional JSON export.
- **Measured Windows release timings (0.1.0 gate, 2026-11-16)**: `49.87 ms` 10k DB open + overview + 500-row page; `5.40 ms` p50 / `10.89 ms` warm p95 / `9.59 ms` cold-cache p95 10k FTS5 search; `29.28 ms` query + `23.76 ms` layout for 1,941-node Namespace graph; release GUI binary `memos-desktop.exe` `18.86 MB` (`19,780,096 B`); standalone `memos.exe` CLI binary `2.69 MB` (`2,816,000 B`). The preview idle pass measured `147–163 ms` first frame; treat idle and busy-host numbers as a range, not a single promise. The full table lives in `README.md`.
- **50k re-measurement (2026-11-20, release build, maximized window)**: `98.4 MB` working set / `88.7 MB` private at 50k nodes with 750 paginated rows. The older `32.14 MB` figure came from the headless smoke harness, which never creates a GPUI window, so it is not a GUI RSS measurement. At 50k the startup phases are `476 ms` GPUI app init (framework, not app code), `26 ms` DB open, `272 ms` overview, `256 ms` first list page, `~615 ms` first frame, `~1.2 s` until the first page is on screen. Idle cost with the window open was measured at about `0.5 s` of CPU per `12 s` (~4% of one core) with the `1.5 s` change-detection poll and GPUI's cursor/wake loop as the suspected contributors. The poll is now event-driven (`src/ui/db_watch.rs`): a `notify` kernel watch on the store's parent directory wakes the reload task only when the database or its `-wal`/`-shm` files change (250 ms burst debounce), with a slow fallback poll (`15 s` active / `60 s` inactive) for missed events and the legacy `1.5 s`/`8 s` cadence only when no watch can be installed (onboarding, missing directory, unsupported backend).
- **List indexing (2026-11-20)**: the schema now carries `idx_nodes_recency_sort` on `(COALESCE(updated_at, created_at, 0) DESC, id DESC)`, matching the list's `ORDER BY` exactly, plus `idx_nodes_provenance` for the facet scan. On a 10k store the 501-row recency page drops from `6.7 ms` (full scan + temp B-tree) to `0.14 ms` (covering index), with the same result set. Existing stores receive these indexes the next time the SDK writer (CLI or MCP) opens them; stores created from the desktop include them from the start.
- **Windows pass (2026-11-27, release, 165 Hz laptop panel, 50k synthetic store from `smoke_bench -- --ignored generate_store`)**: measured back to back against the polish build (`958d92c`), median of 7 fresh launches with `--startup-report`:

  | | before | after |
  |---|---|---|
  | first frame | `260.0 ms` | `255.9 ms` |
  | first list page | `282.8 ms` | `272.1 ms` |
  | overview settled | `339.6 ms` | `330.4 ms` |
  | idle CPU, focused (60 s) | `2.45 %` of one core | `2.00 %` |
  | idle CPU, unfocused (60 s) | `2.50 %` | `2.55 %` |
  | idle CPU, minimized (45 s) | `5.31 %` | `5.17 %` |

  Of the first frame, `~201 ms` is `gpui_app_init` and `~35 ms` is GPUI's window and device setup; the app's own share before the first frame is `~20 ms` (`settings` `13 ms`, which is the process's first cold file read and is needed to size and theme the window; `telemetry_init` `2 ms`, kept early so a startup panic is still scrubbed; `app_view_new` `3 ms`; `first_render` `1.5 ms`). Store work (open, first page, overview, health) already runs after the first frame, so nothing large is left to defer. The 2026-11-20 figure of `~615 ms` was a busier host; compare numbers only within one session.
- **Idle is GPUI's frame loop, not the app.** With `MEMOS_DESKTOP_RENDER_STATS=1` the app logs rendered frames per 10 s: an idle window renders `0` frames, focused or not. GPUI 1.29.2's Windows backend (`gpui-windows` `platform.rs`, `begin_vsync_thread`) calls `RedrawWindow` on every visible window at every vblank, so the UI thread takes a `WM_PAINT` and a `request_frame` callback 165 times a second that ends in "nothing dirty". Minimized windows cost more because DWM stops providing vblanks and the vsync thread falls back to timed sleeps. Getting idle near zero needs GPUI to stop invalidating clean windows (an on-demand redraw request from core plus an idle vsync thread); that is a framework change, not made here. The app-side wakers are gone: the store poll is event-driven, Momo's peek runs at most once per 10 minutes after 3.5 minutes idle, and the graph drift stops when the window is inactive.
- **UI-thread budgets for export and batch review (`smoke_bench`, release, 2026-11-27)**: a 1,000-memory export loads in `19.4 ms` and writes atomically in `1.7 ms`, both on the background executor; the only UI-thread step, building the pack text in the chosen format, takes at most `2.9 ms` (budget `16 ms`). A 1,000-memory batch costs `0.41 ms` of UI thread per decision (budget `4 ms`); before row states were indexed the same update took `7.3 ms`.
- **Two-phase startup (2026-11-20)**: the first paint loads only the node count, contradiction ids and the first page (`load_list_fast_meta`), painting the list before the facet `GROUP BY`s, table counts and health run. At 50k that puts a readable list on screen at `93–96 ms` instead of `180–194 ms`, while the full overview and health settle in phase two (`~257 ms`) without blocking the list.

## 6. Visual Surface & Icon System (`src/ui/views/mod.rs`)

- **Warm obsidian palette**: Dark mode uses `#0B0908` sunken, `#12100E` app canvas, `#1A1714` panel, `#221E1A` elevated, `#28231F` floating, `#2E2823` hairlines, `#241F1A` subtle dividers, `#E8E1D5` primary text, `#C9C0B2` secondary, `#A79D8F` muted, and `#C97B4A` burnt copper accent so dark and light modes feel like one product.
- **Hierarchy & density**: A single-line sidebar **Store card** (`20 px` tabular count + `12 px` label, `3 px` health bar, `N health issues` in the accent color so it is never read as the Review count, muted `Health NN`, whole card opens **Health**) and a one-line list page header (page title at `21/600` plus a `12 px` tabular summary showing `showing N of total` while paginated and `updated <age>`, right-aligned **Filter**/**Sort**) anchor navigation alongside **Today** (daily Brief) and **Review** surfaces. The OS title bar is the only other brand surface; the header slot above the sidebar names the open store and opens **Switch store** (icon only in the compact layout), the sidebar carries no second app mark, and the status bar shows mode (`view only` / `editing on`) without the database filename. List rows drop internal card borders in favor of `64 px` Comfortable / `48 px` Compact spacing (`AppSettings.row_density`), `14/500` titles, `12 px` meta without raw trust decimals, and `tabular_nums()` (`tnum`) counts.
- **Warm surface & motion**: Dark uses `#12100E` / `#1A1714` / `#221E1A` / `#2E2823` / `#E8E1D5` / `#C97B4A`; light splits structural `#D8D1C6` from subtle `#EDE8DF`. Graph type colors are low-chroma warm hues (max saturation ~0.41), not D3 defaults. List-row hover eases over `120 ms`, the page title fades over `180 ms`, and `with_animation` follows GPUI's reduce-motion flag (`--no-fun` / OS preference).
- **Warm glass, not glassmorphism**: Windows requests GPUI's `MicaBackdrop`; the palette, filter/sort/overflow popovers, and Settings/Health/Tools/Composer/Ingest/Context/Dream Diff dialogs use `glass_floating`/`glass_panel` alpha sheets (0.97/0.98), a `1 px` top highlight, 16 px radii, a warm scrim, and `shadow_lg`. Memory rows, the graph, and the detail body stay opaque to protect contrast. There is no per-element backdrop blur in GPUI 1.29; the effect is layered quads, not a sampled background.
- **Shared kit (`src/ui/views/kit.rs`)**: new and reworked surfaces use one set of controls on a 4 px spacing scale (4/8/12/16/20/24) and an 11/12/13/14/20 px type scale: 28 px buttons (primary at most once per dialog, secondary bordered, subtle borderless, danger text-colored and never filled), a disabled button that states why in its accessible label, a segmented control, a `switch_row` (title, one line of explanation, accent track, focus ring), an `icon_button_disabled` with the same footprint as `icon_button`, a `ModalShell` (title, optional subtitle, scrolling body, footer note on the left, actions secondary-then-primary on the right, scrim click and `Esc` to dismiss; `height` and `flush_body` for split-pane dialogs such as Tools) used by every dialog including consent, Tools and Dream diff, hairline-left notices instead of filled banners, two-line empty states, and text state markers with a reinforcing dot so color is never the only signal.
- **One word for conflicts**: the UI says *Conflict(s)* everywhere (rows, inspector, graph mode and legend, Today, Health, Dream diff, the built-in view, which older settings files rename on load). `has:conflict` and the CLI's `has:contradiction` both work.
- **Rows carry one marker**: list rows show at most one state word (Quarantined > Conflict > Low trust > Pinned) next to a tabular age column, so a busy store does not become a wall of badges.
- **Single icon family**: `UiIcon` resolves `Segoe Fluent Icons` (falling back to `Segoe MDL2 Assets`) on Windows via `Window::text_system().all_font_names()`, with safe Unicode symbol fallbacks on macOS, Linux, and headless runs. Fallbacks are ordinary symbols (`▾`, `▴`, `↑`, `↓`), never the U+2303/U+2304 keyboard glyphs most fonts render tiny or not at all.
- **Links have one definition**: a link is a stored edge, counted once per linked memory in either direction; `contradicts` edges and `contradictions` records are *conflicts*, counted separately (`core::model::linked_memory_count`). Graph edges carry `structural` for the same-namespace/tag/entity/timeline/cluster chains that only shape a view; those are never counted, highlighted on selection, or treated as focus neighbours. The graph card, the inspector's *Linked memories* (one row per linked memory) and the graph header all use this count.
- **Graph legibility**: graphs with at most `GRAPH_LABEL_ALL_MAX_NODES` (`24`) memories label every node; larger graphs label the most important nodes with a zoom-scaled budget (`8 × zoom`, `6–48`) plus selected/hovered nodes, all hidden below `GRAPH_AMBIENT_LABEL_MIN_ZOOM` (`0.40`), with importance-ordered collision culling, viewport bounds clamping, and `1 px` text halos; ambient edges render at `35%` alpha (`70%` when highlighted or contradictory) and selected nodes use a soft radial halo behind a crisp `2 px` copper ring.

## 7. First-Run Onboarding & Atomic Settings (`src/ui/views/onboarding.rs`, `src/core/settings.rs`)

- **Trigger & geometry**: launches when `settings.onboarding_completed` is `false` inside a single `1100×720` (min `900×600`) GPUI window following the active `ThemePalette`.
- **Create in place**: when the candidate path holds no store, **Create memory store** runs `core/store_init::create_store` on the background executor (canonical schema, WAL, all indexes and FTS triggers) and then probes the new file, so a clean machine never needs Node, npx, or a terminal to get started.
- **Non-blocking DB validation**: path probing (including native `Browse…` dialogs via `rfd`) executes on GPUI's background executor using a cancel-safe generation counter and verifies both SQLite readability (`SQLITE_OPEN_READ_ONLY`, `PRAGMA query_only = ON`) and the presence of a `nodes` table before advancing.
- **Keyboard-first focus**: because GPUI's focused `.on_click(...)` div elements dispatch activation on `Enter`/`Space`, `OnboardingView::on_key_down` handles `Esc` (step back, never quit) and `Tab`/`Shift-Tab` while only advancing on `Enter` when no interactive button holds focus — preventing double-step skips.
- **Atomic persistence**: `settings.json` writes go to a temp file followed by atomic rename inside the platform config dir or `MEMOS_DESKTOP_HOME`.

## 8. Harnesses Discovery & Temporary-Config Launch (`src/core/harness/`)

- **Full `memos connect` parity (`16` targets)**: covers all 15 `memos connect` targets (Claude Code, Codex, Cursor, Windsurf, Cline, OpenCode 2.x default, OpenCode 1.x legacy, Gemini CLI, Hermes Agent, `.dsh`, Kilo, Pi, OpenClaw, Zed, Goose) plus Continue, flagging print-only targets cleanly and keeping `.dsh` scoped to `$DSH_HOME`/`~/.dsh/memos.patch.yml` (or detected `dsh` binary) without touching `cordis.patch.yml`. Probes `opencode --version` so only the installed major (2.x vs 1.x) is marked active.
- **Bounded `< 100 ms` discovery**: fixed config path checks and directory-indexed `PATH` lookups across all 16 adapters use mtime/version caching so repeated modal opens avoid redundant process spawns.
- **Non-mutating launch**: **Connect** passes `MEMOS_DB` and generated temporary MCP configuration arguments/files where supported, keeping external global harness config files untouched (`applied = false`).

## 9. Workbench Workflows (`src/ui/app/`)

`app.rs` holds only the `MemOSApp` struct, its supporting types and window launch (under 600 lines). Behaviour lives in child modules of `ui::app` by concern: `state` (construction, theme, notices, popovers), `keymap` (bindings and global keys), `actions` (navigation, filters, palette commands), `loaders` (every background read, store watching), `write_path` (everything that changes the store, all through the `WriteBridge`), `modals`, `settings_ui`, `tools_ui`, `shell` (the root `Render`), and the workflow modules (`pack_ui`, `capture_ui`, `compare_ui`, `search_ui`, `health_ui`, `review_batch`, `store_ui`, `dialogs_ui`, `shortcuts`); their pure logic is in `core::{context_pack, capture, compare, health}` with unit tests.

- **Context packs stay local and faithful.** Items load on the background executor through read-only, schema-introspected SELECTs (`load_context_items_for_filter`, capped at 60 for a view; `load_context_items_by_ids` for pins). Budgets drop whole memories and report how many; sizes are computed arithmetically so switching format or budget does not re-assemble the payload per candidate.
- **Capture and compare respect the write boundary.** Quick capture builds a `StoreInput` and goes through the existing `WriteRetryAction::Store` path (same banner, retry and reload). Comparison loads both memories read-only; its Forget buttons render only in write mode and reuse the existing confirmation modal.
- **Pins are local UI state.** They live in `settings.json` keyed by store path (atomic temp+rename writes, at most 100 per store, 20 stores), are pruned when a pinned id no longer loads, and are never written into SQLite or exported as memory metadata.
- **Export writes one file, never the store.** Packs are built from read-only SELECTs (`load_context_items_by_ids`, `load_context_items_for_filter` capped at 1,000 for "No limit"), then written to the path from GPUI's `prompt_for_new_path` via a temporary sibling and rename on the background executor. With no save dialog available the app saves to the documents/home folder and names it in the status bar.
- **Batch review is sequential and honest.** `memos_review` takes one id, so a batch is a loop of independent writer calls on the background executor; progress is mirrored into the Review view after every item, each row in the run shows its own state (Waiting, Approving…, Approved, Failed, Not attempted) through an id index, Stop takes effect between items, a missing `memos_review` capability stops the run immediately, and the summary reports succeeded, failed and not-attempted counts. A finished summary clears as soon as the user starts something new.
- **Review links to Compare.** Candidates with a recorded conflict show a *Conflict* marker and **Compare** (also in view-only mode, since it only reads). `open_compare` with no right-hand id resolves the first conflicting memory in the same background read.
- **Store switching reuses startup.** The candidate is probed with the read-only `probe_database` off the UI thread; on success the shared connection is invalidated, the writer is reconfigured for the new path, per-store state (filter, selection, pack, overview) resets, and the normal two-phase initial load runs.
- **Recent searches** are stored next to saved views in `settings.json` (newest first, capped at 8, clearable). Like saved views they never leave the machine and are not part of diagnostics.
- **Recent palette commands** persist in `settings.json` (`recent_commands`, newest first, 4). Only built-in command titles are written; memory titles, saved-view names and store paths never are, and renamed or removed commands drop out on load.
- **Export from the keyboard.** `Ctrl/Cmd+E` opens the pack in export mode (no budget, Markdown, **Save…** as the primary action); pressing it again saves.

## 10. Code Safety & Checks

- **`unsafe` lives in one module.** `Cargo.toml` denies `unsafe_code`; `src/win32.rs` (Windows only) is the single module allowed it and holds the titlebar DWM calls, the reduced-motion query and the working-set probe used by the smoke benchmarks, each block with a `// SAFETY:` comment. Tests mutate environment variables only through two `ENV_LOCK`-guarded helpers in `core::harness::adapters`.
- **No panicking unwraps in production code.** `clippy::unwrap_used` warns outside tests (`clippy.toml` allows it in tests) and CI denies warnings.
- **CI (`.github/workflows/desktop-gpui.yml`)** runs on Linux, macOS and Windows for pushes to `main`/`dev` and every pull request touching the app: `cargo fmt --check`, release Clippy for the GUI and the CLI-only build, library, CLI-only, crash-scrubber and smoke-benchmark tests, a release build and `--self-test`. Dependabot proposes weekly grouped cargo updates (the pinned `gpui` crates are excluded).
- **Profiling builds.** `cargo build --profile profiling` gives optimised binaries without LTO for quick measurement; numbers recorded here come from the release profile.
