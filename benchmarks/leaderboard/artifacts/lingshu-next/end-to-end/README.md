# Lingshu Next (灵枢 Next), LongMemEval-S Track B

The 2026-11-27 Windows desktop build answered all 500 questions in the organizer's original S split. DeepSeek Flash generated the answers, then DeepSeek V4 Pro judged the sealed responses. The score was **328/500 (65.6%), provisional**. One run is available for this build. Its sample standard deviation is undefined. The dataset and evaluation prompt were downloaded at pinned revisions. [Leaderboard protocol](https://memos.readthedocs.io/en/latest/benchmark-leaderboard/) · [Original LongMemEval project](https://github.com/xiaowu0162/LongMemEval)

## Reproduce from a clean checkout

Use Windows x64, Node.js 24.19.0 (bundled SQLite 3.53.3), Python 3.12 and DeepSeek Harness desktop **0.2.2-rc.3**. The measured machine has an AMD Ryzen 9 7845HX, 24 logical processors. The account path requires the two published model IDs to remain available to your account. The public script launches the installed official SDK in a fresh text-only profile for each question. Authentication, account billing and token refresh are handled by the provider's own plugins. There are no npm or pip dependencies. [DeepSeek Harness release](https://github.com/deepseek-ai/deepseek-harness/releases/tag/dsh-v0.2.2-rc.3)

Set `DSH_BENCH_INSTALL` to the installation directory containing `DeepSeek Harness.exe`. The runner verifies the installed executable and archive by SHA-256. The official Windows x64 installer for this version has SHA-256 `786c9b26050c35b62c7be6a01dee2541dc1c2c5d9bd5f2dbe77beeeb8d50704e`. Its Windows Authenticode publisher is Hangzhou DeepSeek Artificial Intelligence. [Official Windows installer](https://download.deepseek.com/dsh-desk/bin/win-x64/deepseek-harness-0.2.2-rc.3-win-x64.exe)

Use a dedicated benchmark account. Sign in through DeepSeek Harness for that account, then set `DSH_BENCH_ACCOUNT_STORE` to the absolute path of its local Harness credential-store file. The SDK's default local store is `.credentials.yaml` in that profile's Harness home. A deployment with an explicit local-store path uses its configured path. The runner accepts the path and supplies it to the official credentials plugin. Keep the store and the private run directory outside a published repository. Choose a neutral absolute path for output, such as a benchmark folder on a dedicated drive. The SDK sends its empty per-question working directory's absolute path to the model in its runtime-context message. [Official credential-store options](https://github.com/deepseek-ai/deepseek-harness/tree/dsh-v0.2.2-rc.3/packages/credentials/credentials-local)

From the checkout root, run these PowerShell commands. Replace the two example paths with your own installation and dedicated account store. On hosts with several Python installations, set `PYTHON` to the Python 3.12 executable.

```powershell
$env:DSH_BENCH_INSTALL = 'D:\Apps\DeepSeek Harness'
$env:DSH_BENCH_ACCOUNT_STORE = 'D:\BenchmarkAccount\.credentials.yaml'
$a = 'benchmarks/leaderboard/artifacts/lingshu-next/end-to-end'
curl.exe --fail --location 'https://huggingface.co/datasets/xiaowu0162/longmemeval/resolve/2ec2a557f339b6c0369619b1ed5793734cc87533/longmemeval_s' --output longmemeval_s
node "$a/audit.mjs" longmemeval_s
node "$a/run.mjs" probe longmemeval_s ../next-probe-private
node "$a/run.mjs" run longmemeval_s ../next-rerun-private
```

The audit reimports all 500 histories into fresh SQLite databases and checks every generated reader-prompt digest against the original observations. It also verifies the committed result digest and counts the recorded verdicts. The probe initializes and shuts down the official SDK with an empty store. Both use zero model calls. The final command generates 500 new answers and 500 new judgments using the account's provider route. It writes ordered result rows and a measurement summary in the private output directory. Cloud responses can vary. For a one-question provider check append `1` to the final command and use a different fresh output directory.

Fresh runs use four concurrent requests. Each available slot starts the next question immediately. Set `DSH_BENCH_CONCURRENCY=1` for the original desktop run's concurrency, or select a limit from 1 to 4. Resume inherits the saved concurrency unless explicitly configured. Each phase finishes all in-flight work before the next phase begins, and the exported results follow the organizer's question order. A fresh private output stores a read-only, digest-checked snapshot of the organizer file (278,025,796 bytes). Both phases use the same snapshot. Resume revalidates it, or creates one from the pinned dataset for older checkpoints. The runner records a terminal state for every reader request before loading the reference-answer projection. Each SDK attempt has separate startup, pre-dispatch, acknowledgement and wait markers. A failed startup can be tried a second time when the ledger proves that dispatch had not begun. A potentially dispatched call without a confirmed response contributes an unresolved verdict and zero credit. A missing answer receives no judge call. Each committed answer and verdict is retained.

To continue an interrupted run, keep the dataset, concurrency, limits, account and output path identical and replace `run` with `resume`. The runner acquires an exclusive local lock, verifies sealed answers and their rebuilt prompt hashes, and skips completed judgments. A legacy startup marker without a confirmed answer is conservatively treated as an unknown dispatch. Original usage remains null for an unknown call. The runner validates the loaded reader and judge templates against their published hashes. A rubric exceeding the 8,192-byte judge input budget receives no judge call and zero credit. The sealed answer and rubric digest are retained. Full-run accuracy is emitted only after all 500 terminal rows validate. Legacy runs without a run configuration also need their original measurement summary for migration. The original measurement had no unresolved rows.

## Ingestion and scoring

The input projection passes only the raw message roles, text, dates and positional session ordinals to the reader adapter. The user query and organizer question date enter during retrieval. An opaque, deterministic ID identifies each historical session and message. The index stores original user turns with a local lexical posting list. Direct matches and neighboring user turns are filtered for eligibility, ranked and packed within the normal limits of 64 source messages and 24,000 retrieval characters. The reader's complete user payload is capped at 8,000 UTF-16 code units. Each run of the reported build used a fresh query session, without memory writeback. The benchmark created no saved facts and used no LLM during ingestion, embeddings, external reranker or post-generation answer editing.

Sources are grouped by session in relevance order, then by timestamp and message position within each group. The reader sees the question, its timestamp, empty conversation and fact lists, and compact source records with their original text and UTC timestamps. The highest observed packed counts were 25 messages and 18 sessions. Each question had at least 39 candidate sessions. This track uses a message and character budget, with no fixed session top-k.

Temperature was not supplied for either model. Both models used the pinned Harness `deepseek-account` route with reasoning effort `off`. The SDK did not expose a numeric temperature and used provider defaults. The reader's SDK output cap was 2,048 tokens and the judge's was 64. Both received their declared system and user messages and the SDK's working-directory context for an empty workspace. The judge applied the organizer's task-specific rubric. Only a trimmed, lowercased exact yes or no was accepted. Every question counts in the denominator, including all 30 abstention items. There were zero unresolved verdicts. [Pinned upstream rubric](https://github.com/xiaowu0162/LongMemEval/blob/9e0b455f4ef0e2ab8f2e582289761153549043fc/src/evaluation/evaluate_qa.py)

The original measurement used the normal Next desktop chat host and its account provider. The public adapter implements the fresh benchmark database case, uses the identical frozen lexical ranker, and reproduces the chat packing with the publicly disclosed recipe. The SDK profile preserves the model configuration, content order and zero advertised tools. The local SDK event stream confirms one system message, one user message, one working-directory reminder, the request header and provider context, one committed answer, and a completed turn, in that order. The evidence reaches the local SDK boundary. Cloud-side transformations and network payloads beyond that boundary were not observed. It omits the desktop UI, account-management bridge and unrelated production capabilities. The 500 original prompt SHA-256 values matched the public adapter. Independently rendering the 500 judge inputs from the sealed original answers matched all 500 original rubric digests. An account-backed one-question smoke test of the public harness produced one reader response and one judge verdict.

Each published JSONL row contains the organizer's question ID, category, counters, durations, verdict and hashes. Reader and reference text, source histories, SDK logs, credential state and private development/holdout records are excluded. Timings sum separate reader and judge stage durations and exclude idle time between phases. The median sum was 7,006.5 ms. Provider-reported totals were 1,451,881 reader tokens and 223,549 judge tokens, or 3,350.86 combined per question. Account debit amounts and ingest timings for this original round are unavailable.
